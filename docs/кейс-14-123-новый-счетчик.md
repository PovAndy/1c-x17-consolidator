# Кейс 14-123: новый счетчик виден, но начисление в x17 равно 0

## Короткий итог

Кейс `14-123` доведен до точной причины.

Проблема находится не в истории услуги ЛС и не в самом наличии показаний.  
Корень дефекта в `x17` такой:

1. новый прибор `хвс` имеет показания и объем в карточке ЛС;
2. но его `ВидПрибораУчета.ВидУслуги` не совпадает с видом услуги, по которой считается начисление;
3. из-за этого форма ЛС показывает объем прибора, а расчет начислений этот же прибор отбрасывает и берет `0`.

## База и ЛС

1. проблемная база: `x17`
2. эталон: `x1-14`
3. ЛС: `14-123`
4. абонент: `Шульпекова Антонина Николаевна`
5. объект учета: `п. Искра, ул. Тольятти, д. 11`

## Что видно по данным

### В `x17`

1. на ЛС есть новый прибор `хвс`;
2. по нему есть показания:
   - `01.03.2026 = 1`
   - `25.03.2026 = 6`
3. в карточке ЛС виден объем марта:
   - `5`
4. услуга `Холодное водоснабжение по приборам учета` подключена;
5. комментарий расчета за март 2026 показывает:
   - `Показания приборов учета = 0`
   - результат начисления `0`

### В `x1-14`

1. визуально картина по этому же ЛС совпадает;
2. при этом комментарий расчета за март 2026 показывает:
   - `Показания приборов учета = 5`
   - результат начисления `300`

## Что было проверено и исключено

Для `14-123` уже проверено и больше не является главной гипотезой:

1. `икУслугиЛицевыхСчетов`
2. `икОпределениеПредоставляемыхУслугЛицевыхСчетов`
3. история подключения услуги с `01.03.2026`
4. отсутствие показаний как таковых

По логам `x17` и `x1-14` служебный слой `ЛС -> услуга` совпадает.

## Точная причина

### Что делает расчет в `x1-14`

В распакованной конфигурации `x1-14` подтверждено:

1. подбор прибора в расчете выполняется в:
   - [икНачисления/Module.bsl]({PROJECT_ROOT}/context/config-dumps/x1_14/CommonModules/икНачисления/Ext/Module.bsl)
2. критическое условие:
   - `икИндивидуальныеПриборыУчета.Владелец = ОбъектУчета`
   - `икИндивидуальныеПриборыУчета.ВидПрибораУчета.ВидУслуги = ВидУслуги`
3. получение объема по прибору идет в:
   - [икПриборыУчета/Module.bsl]({PROJECT_ROOT}/context/config-dumps/x1_14/CommonModules/икПриборыУчета/Ext/Module.bsl)
4. там есть дополнительный фильтр:
   - `И ПриборУчета.ВидПрибораУчета.ВидУслуги В (&МассивВидовУслуг)`

### Почему карточка ЛС может показывать объем, а расчет — нет

В форме ЛС объемы приборов выводятся через запрос к:

- [ФормаЭлемента/Module.bsl]({PROJECT_ROOT}/context/config-dumps/x1_14/Catalogs/икЛицевыеСчета/Forms/ФормаЭлемента/Ext/Form/Module.bsl)

Там объем из `икОбъемПотребленияПоПриборамУчета` подтягивается:

1. по `ОбъектУчета`
2. по списку приборов
3. по `ТарифнойЗоне`, если она есть

Но в этом запросе нет того жесткого фильтра по:

- `ПриборУчета.ВидПрибораУчета.ВидУслуги`

который использует сам расчет начислений.

### Практический смысл

Именно поэтому в `x17` возможна такая ситуация:

1. карточка ЛС показывает объем прибора `5`;
2. но расчет начислений считает, что этот прибор не относится к нужному виду услуги;
3. в итоге в комментарии расчета получается:
   - `Показания приборов учета = 0`

## Правильный способ исправления

Исправлять нужно не услугу ЛС, а приборный слой:

1. найти проблемный новый прибор;
2. определить активную услугу ЛС;
3. определить правильный канонический `ВидПрибораУчета` для этой услуги;
4. перепривязать прибор на этот канонический `ВидПрибораУчета`;
5. пересчитать начисление.

## Что сделано в EPF

В `v25-118.45` добавлен отдельный адресный сценарий `[7]`:

1. `[7] Диагностика новых счетчиков`

   - существует ровно один канонический кандидат `ВидПрибораУчета` для нужной услуги;

## Что показал `118.50`

Логи `118.50` подтвердили по `14-123`:
1. проблемный прибор — именно `хвс`, код `00-000002`;
2. он подключён и даёт `ОбъемМесяца = 5`;
3. у него mismatch по виду услуги:
   - текущий `ВидУслугиПрибора[ключ] = 3aca73b2-...`
   - целевой `ВидУслуги = 013f226e-...`
4. значит расчёт не берёт этот прибор не из-за отсутствия показаний, а из-за неверного приборного классификатора.

Одновременно `118.50` показал, что в базе для этого случая не существует готового безопасного канонического `ВидаПрибораУчета`, поэтому одного простого `RELINK` недостаточно.

## Что добавлено в `118.51`

В `118.51` сценарий `[7]` стал глубже и осторожнее.

### Углублённая диагностика

Теперь в отчёте дополнительно видны:
1. активная услуга ЛС, к которой должен относиться новый прибор;
2. настройка услуги:
   - `УчитыватьПоказанияПриборовУчетаТолькоУказанныхВидов`;
3. сколько строк допустимых видов приборов записано в услуге;
4. все `икВидыПриборовУчета` с тем же именем, что у текущего прибора;
5. все `икВидыУслуг` с тем же именем, что у целевой услуги;
6. статистика использования текущего вида прибора:
   - в ИПУ;
   - в КПУ;
   - в настройках услуг.

### Режимы исправления

`118.51` использует три режима:
1. `RELINK`
   - когда найден ровно один безопасный канонический вид прибора;
2. `UPDATE_CURRENT_KIND`
   - когда текущий вид прибора используется только этим прибором и услуга не ограничивает список допустимых видов;
3. `CREATE_CLONE`
   - когда текущий вид прибора используется ещё где-то, но услуга не ограничивает список допустимых видов; тогда создаётся отдельный клон вида прибора под нужную услугу и сам прибор переводится на этот клон.

Если услуга ограничивает допустимые виды и готового канона нет, автоматическое исправление не делается — это правильно и безопасно.

## Что показал `118.51`

`118.51` подтвердил, что по `14-123` выбран правильный режим исправления:
1. `РежимИсправления = CREATE_CLONE`
2. то есть данные базы действительно требуют отдельного вида прибора под нужную услугу, а не простого relink на уже существующий канон.

Одновременно `118.51` показал технический сбой самой обработки:
1. при создании клона она пыталась записать `Родитель`;
2. в текущей базе `икВидыПриборовУчета` не является многоуровневым справочником;
3. поэтому исправление упало на ошибке:
   - `Справочник не многоуровневый`.

## Что исправлено в `118.52`

В `118.52` создание клона вида прибора стало совместимым с обеими схемами базы:
1. если каталог иерархический — `Родитель` копируется;
2. если каталог неиерархический — `Родитель` вообще не трогается.

Это не меняет логику восстановления, а убирает технический блокер, который мешал применить уже найденный правильный режим исправления.
