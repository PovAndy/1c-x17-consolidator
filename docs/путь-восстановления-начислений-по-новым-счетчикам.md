# Путь восстановления начислений по новым счетчикам в x17

Документ собран по распаковке `x1-14`, логам `x17` и финальному разбору кейса `14-123`.

## Финальный вывод

Если на ЛС новый счетчик:

1. виден в карточке;
2. имеет показания;
3. в карточке ЛС по нему виден объем;
4. но начисление остается `0`,

то первым делом нужно проверять **не слой услуг ЛС**, а соответствие:

1. `ПриборУчета.Владелец`
2. `ПриборУчета.ВидПрибораУчета`
3. `ПриборУчета.ВидПрибораУчета.ВидУслуги`
4. активной услуги на ЛС

Для `x17` это и есть правильный путь восстановления.

## Что доказано по конфигурации x1-14

### Подбор прибора для расчета

В `x1-14` прибор попадает в расчет только если одновременно выполняются условия:

1. `икИндивидуальныеПриборыУчета.Владелец = ОбъектУчета`
2. `икИндивидуальныеПриборыУчета.ВидПрибораУчета.ВидУслуги = ВидУслуги`

Опорный файл:
- [икНачисления/Module.bsl]({PROJECT_ROOT}/context/config-dumps/x1_14/CommonModules/икНачисления/Ext/Module.bsl)

### Чтение объема по прибору

В расчете объема по приборам есть дополнительный фильтр:

- `И ПриборУчета.ВидПрибораУчета.ВидУслуги В (&МассивВидовУслуг)`

Опорный файл:
- [икПриборыУчета/Module.bsl]({PROJECT_ROOT}/context/config-dumps/x1_14/CommonModules/икПриборыУчета/Ext/Module.bsl)

### Почему карточка ЛС может ввести в заблуждение

В форме ЛС объем прибора может отображаться даже при неверном виде услуги у прибора, потому что запрос формы соединяет объемы по:

1. `ОбъектУчета`
2. списку приборов
3. `ТарифнойЗоне`

но без того строгого фильтра по:

- `ПриборУчета.ВидПрибораУчета.ВидУслуги`

Опорный файл:
- [ФормаЭлемента/Module.bsl]({PROJECT_ROOT}/context/config-dumps/x1_14/Catalogs/икЛицевыеСчета/Forms/ФормаЭлемента/Ext/Form/Module.bsl)

## Точная причина проблемы в x17

Для кейсов вроде `14-123` уже подтверждено:

1. `икУслугиЛицевыхСчетов` совпадает с `x1-14`
2. `икОпределениеПредоставляемыхУслугЛицевыхСчетов` совпадает с `x1-14`
3. показания нового прибора есть
4. объем прибора в карточке ЛС может быть виден

Но начисление все равно равно `0`, если:

1. новый прибор имеет неверный `ВидПрибораУчета`;
2. а его `ВидПрибораУчета.ВидУслуги` не совпадает с активной услугой ЛС.

Тогда:

1. карточка ЛС показывает объем прибора;
2. а расчет начислений этот прибор отбрасывает.

## Правильный путь восстановления

### Для одного ЛС

1. Открыть `v25-118.45`
2. Указать номер ЛС
3. Выполнить:
   - `[7] Диагностика новых счетчиков`
   - `[7] Preview новых счетчиков`
   - `[7] Исправить новые счетчики`
4. Пересчитать начисление за нужный месяц
5. Проверить комментарий расчета

### Что делает `[7]`

Новый сценарий `[7]`:

1. берет выбранный ЛС;
2. собирает активные услуги ЛС;
3. собирает приборы, статусы и объемы по приборам;
4. определяет целевой `ВидУслуги` для расчета;
5. ищет канонический `ВидПрибораУчета` для этой услуги;
6. если найден ровно один безопасный кандидат, перепривязывает прибор на этот канонический `ВидПрибораУчета`.

### Для всей базы

После подтверждения на контрольных ЛС массовый маршрут такой:

1. снять `[7] Диагностика новых счетчиков` по проблемным ЛС;
2. выделить кандидатов, где:
   - прибор подключен;
   - по прибору есть объем;
   - начисление по услуге равно `0` или не использует этот объем;
   - `ВидПрибораУчета.ВидУслуги` не совпадает с активной услугой;
3. выполнить `[7] Исправить новые счетчики`;
4. пересчитать начисления по затронутым периодам.

## Что больше не является главным направлением

Для этого класса проблем уже не нужно в первую очередь:

1. переигрывать `икУслугиЛицевыхСчетов`
2. переигрывать `икОпределениеПредоставляемыхУслугЛицевыхСчетов`
3. лечить кейс через восстановление broken refs

Эти пути были полезны как диагностика, но точным корнем проблемы не являются.

## Критерий успешного восстановления

Для контрольного кейса вроде `14-123` после исправления должно получиться:

1. `Показания приборов учета = 5`
2. начисление за март 2026 = `300`
