## Короткий вывод

Стандартную обработку имеет смысл использовать только для простых безопасных хвостов.
Для наших текущих боевых дублей ПВХ и битых ссылок она не должна быть основным инструментом.

## 1. Можно рассматривать для стандартной обработки

Только после контрольной проверки ссылок и только как позднюю чистку хвоста.

### Хвосты `tail_no_refs` в ПВХ

#### икХарактеристикиОбъектовУчета
- `ДУБЛЬ (Не используется) Ранее присвоенный инвентарный номер (ГИС ЖКХ)`
- `ДУБЛЬ (Не используется) Ранее присвоенный кадастровый номер (ГИС ЖКХ)`
- `ДУБЛЬ Кадастровый номер (ГИС ЖКХ)`

#### икХарактеристикиПрочихОбъектов
- `ДУБЛЬ Алгоритм подписи (ГИС ЖКХ)`
- `ДУБЛЬ Вид услуги (в регл. отчете "Форма 1-ПУ")`
- `ДУБЛЬ Дата пломбировки прибора учета`
- `ДУБЛЬ Идентификатор сотрудника, сформировавшего ответ (ГИС ЖКХ)`
- `ДУБЛЬ Информация о поверке прибора учёта`
- `ДУБЛЬ Код района (ГЦЖС)`
- `ДУБЛЬ Коллективный ПУ для коммунальной квартиры (ДомОкей)`
- `ДУБЛЬ Марка прибора учёта`
- `ДУБЛЬ Наличие технической возможности автоматического расчета потребляемого объема ресурса (ГИС ЖКХ)`
- `ДУБЛЬ Номер антимагнитной пломбы ("МИД" 35.19.18_дублирующий элемент_вА)`
- `ДУБЛЬ Номер антимагнитной пломбы ("МИД" 35.19.18_основной элемент_аА)`
- `ДУБЛЬ Номер пломбы`
- `ДУБЛЬ Тип прибора учета (для реестров Сбербанка)`

Почему это допустимо:
- по focused-инвентарю у этих хвостов нет живых ссылок;
- они уже выглядят как исторические хвосты после прошлых восстановлений;
- тут задача ближе к штатной: выбрать канон, заменить ссылки при необходимости, удалить дубль.

## 2. Только после адресной ручной проверки

### `live_no_refs`

#### икХарактеристикиОбъектовУчета
- `Высота помещения`
- `Есть индивидуальный источник отопления (автономное отопление)`
- `Количество лестниц`
- `Количество лифтов`
- `Количество этажей`
- `Номер по плану`
- `Площадь мест общего пользования`
- `Характеристики ГИС ЖКХ`
- `Характеристики ГЦЖС`

#### икХарактеристикиПрочихОбъектов
- `Идентификатор сотрудника, сформировавшего ответ (ГИС ЖКХ)`

Почему только после ручной проверки:
- в focused-регистрах ссылок нет, но элементы активные;
- часть из них может быть структурной нормой, а не мусором;
- для групп/папок и системных веток риск ложного объединения выше, чем выгода.

Решение:
- сначала диагностировать нашей обработкой;
- типовую обработку использовать только для редких простых пар, где канон очевиден и структура не страдает.

## 3. Нельзя отдавать стандартной обработке как основной способ

### `unsafe_live`

#### икХарактеристикиОбъектовУчета
- `Жилая площадь`
- `Общая площадь`

#### икХарактеристикиПрочихОбъектов
- `Номер пломбы`
- `Номер антимагнитной пломбы`
- `Информация о поверке`
- `Антимагнитная пломба`

Почему нельзя:
- у них есть живые ссылки в рабочих регистрах;
- у нас уже были точечные восстановительные сценарии для этих семейств;
- тут нужен не просто merge, а выбор канона, перепривязка регистров и контроль бизнес-логики.

### Битые ссылки и восстановление структуры
- broken refs в регистрах характеристик;
- структурные аномалии жилой ветки;
- перенос/скрытие характеристик по эталону x1;
- санирование имен дублей.

Почему нельзя:
- типовая обработка работает по сценарию «поиск дубля -> замена ссылок -> удаление/объединение»;
- она не восстанавливает отсутствующий канон, не чинит broken refs и не выравнивает структуру ПВХ по эталону.

## 4. Практический список для x17

### Можно планировать в типовую обработку
- только поздний хвост `tail_no_refs` после контрольного пересчета ссылок.

### Можно точечно, но с ручной проверкой
- отдельные пары `live_no_refs`, если это не группы, не системные ветки и канон очевиден.

### Не трогаем типовой обработкой
- все текущие боевые `unsafe_live`;
- все broken refs;
- все структурные исправления ПВХ.

## 5. Рабочая рекомендация

Для x17 стандартная обработка полезна как вспомогательный этап финальной санитарной чистки.
Основной инструмент для текущего stabilization-pass — наша адаптивная обработка.
