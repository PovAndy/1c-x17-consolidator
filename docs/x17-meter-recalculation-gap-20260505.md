# x17: восстановление перерасчета после отсутствия показаний ИПУ

Дата: 2026-05-05
Версия обработки после технического фикса: v25-121.19

## Что проверено

- Свежие отчеты `logs/121.18+` показывают, что диагностический контур новых счетчиков снова находит кандидатов, но фиксация падала на `Метод объекта не обнаружен (Свойство)` в функции подбора короткого имени вида прибора учета.
- В `v25-121.19` исправлена техническая ошибка: для `Соответствие` используется `Получить()`, а не `Свойство()`.
- В распакованной x1_14 изучены участки:
  - `CommonModules/икПриборыУчета/Ext/Module.bsl`
  - `CommonModules/икРасчетНачислений/Ext/Module.bsl`
  - `Documents/икВводПоказанийИндивидуальныхПриборовУчета/Ext/ObjectModule.bsl`
  - `Documents/икПерерасчетНачисленийЗаУслуги/Ext/ObjectModule.bsl`
  - `InformationRegisters/икНастройкиУслуг.xml`

## Вывод по механизму

Штатный алгоритм состоит из двух частей.

1. При начислении без показаний расчет пишет объем услуги в `РегистрНакопления.икОбъемПотребленияУслуг` с источниками:
   - `ОбъемПриОтсутствииПоказанийПоНормативу`
   - `ОбъемПриОтсутствииПоказанийПоСреднему`
   - `ОбъемПриОтсутствииПоказаний`

2. При последующем расчете по показаниям модуль `икРасчетНачислений` сравнивает фактический объем по ИПУ с ранее начисленным объемом при отсутствии показаний. Если получается отрицательный объем, он формирует сторно/перерасчет по ранее начисленным периодам.

Критичные настройки услуги в `икНастройкиУслуг`:

- `ИспользоватьНормативПриОтсутствииПоказанийПрибораУчета`
- `ИспользоватьСреднемесячныйОбъемПриОтсутствииПоказанийПрибораУчета`
- `КоличествоМесяцевНачисленийПоСреднему`
- `ОграничениеПериодаОтниманияПриОтсутствии`
- `НачислятьОтрицательныеОбъемыПоТекущемуТарифу`
- `ПолучатьСреднемесячныйОбъемСДатыПоследнегоПоказания`

## Почему перерасчет мог не сработать после слияния

Если в момент первого показания после пропуска в базе были нарушены связи счетчика/вида услуги или отсутствовали корректные движения `икОбъемПотребленияУслуг` с источниками `ОбъемПриОтсутствии...`, автоматический перерасчет не сформировался. После следующих ежемесячных показаний система уже видит предыдущим показанием прошлый месяц, поэтому старый разрыв 2-3 месяца назад не попадает в обычный автоматический сценарий.

То есть повторный текущий ввод показаний сам по себе уже не обязан поднять старый пропущенный перерасчет.

## Правильный способ восстановления

Для проблемных ЛС надо запускать штатный перерасчет прошедших месяцев через документ `икПерерасчетНачисленийЗаУслуги`:

- `ЛицевойСчет`: проблемный ЛС.
- `ПерерассчитываемыйПериод`: месяц, за который не прошел перерасчет.
- `Дата`: текущий расчетный месяц, не раньше начала расчетного периода организации.
- `ПравилоПерерасчетаУслуг`: `ПоВсемУслугам` или точечно по услуге ХВС, если требуется ограничить расчет.
- `СписокУслуг`: ХВС/услуга по прибору, если используется точечный режим.

Проведение документа вызывает `икРасчетНачислений.ОбработкаПроведенияПерерасчетНачисленийЗаУслуги` и пишет движения `икНачисленияЗаУслуги` с видом движения `Перерасчет`.

## Что надо автоматизировать в обработке следующим шагом

Нужен безопасный диагностический сценарий перед массовым созданием документов перерасчета:

1. Найти ЛС с ИПУ по ХВС, где были периоды без показаний и начисления по источникам `ОбъемПриОтсутствии...`.
2. Проверить, что после периода отсутствия есть более поздние показания ИПУ.
3. Проверить, что за старый период нет документа `икПерерасчетНачисленийЗаУслуги` с движениями `ВидДвиженияРасчета = Перерасчет`.
4. Вывести кандидатов: ЛС, услуга, месяц пропуска, начислено по отсутствию, фактический объем по ИПУ после возврата показаний, ожидаемый знак перерасчета.
5. Только после диагностики делать preview создания документов перерасчета.
6. Только после preview создавать и проводить документы перерасчета.

## Визуальная проверка

До исправления:

- Карточка расчетов ЛС за период с месяцем пропуска: нет отрицательной строки перерасчета.
- Документы `Перерасчет начислений за услуги`: нет документа по ЛС и нужному `ПерерассчитываемыйПериод`.
- Комментарий расчета по ХВС: нет сторно ранее начисленного объема при отсутствии показаний.

После исправления:

- В списке документов есть проведенный `Перерасчет начислений за услуги` по ЛС и нужному периоду.
- В карточке расчетов появляется отрицательная/корректирующая строка за ХВС.
- В движениях `икНачисленияЗаУслуги` есть записи с `ВидДвиженияРасчета = Перерасчет`.

## v25-121.20: безопасный сценарий [19]

Добавлен отдельный сценарий восстановления пропущенных перерасчетов ИПУ после возврата показаний:

1. `[19] Диагностика перерасчетов ИПУ` — только чтение, ищет месяцы с объемом при отсутствии показаний и последующими показаниями ИПУ без проведенного документа перерасчета.
2. `[19] Preview перерасчетов ИПУ` — показывает штатные документы `икПерерасчетНачисленийЗаУслуги`, которые будут созданы.
3. `[19] Создать перерасчеты ИПУ` — создает и проводит штатные документы перерасчета, регистры напрямую не меняет.

Период поиска по умолчанию: с `01.01.2026` по конец текущего месяца. Визуальная проверка после фикса: список документов `Перерасчет начислений за услуги`, карточка расчетов ЛС, комментарии расчета созданного документа.

Уточнение безопасности v25-121.20: существующий перерасчет считается покрывающим кандидата только если он проведен за тот же ЛС/месяц и либо пересчитывает все услуги, либо пересчитывает по списку и содержит конкретную услугу кандидата. Это исключает пропуск водного перерасчета из-за чужого перерасчета по другому списку услуг.

## v25-121.21: исправление проверки существующих перерасчетов

Исправлена ошибка диагностики `[19]`: запрос проверки существующего перерасчета больше не делает левое соединение с табличной частью `СписокУслуг`, которое в x17 давало `Неоднозначное поле "СписокУслуг.Услуга"`.

Проверка разделена на два безопасных запроса:

1. проведенный перерасчет за тот же ЛС/месяц с правилом `ПоВсемУслугам`;
2. проведенный перерасчет за тот же ЛС/месяц с правилом `ПоСпискуУслуг`, где в табличной части есть конкретная услуга кандидата.

Это сохраняет точность: перерасчет по чужому списку услуг не закрывает кандидата по воде.

## v25-121.22: полный отказ от запроса к табличной части `СписокУслуг`

В x17 запрос к `Документ.икПерерасчетНачисленийЗаУслуги.СписокУслуг` продолжал давать `Неоднозначное поле "СписокУслуг.Услуга"`. В v25-121.22 проверка существующего перерасчета по правилу `ПоСпискуУслуг` переведена на объектную модель: сначала выбираются проведенные документы за тот же ЛС/месяц с правилом `ПоСпискуУслуг`, затем их табличная часть `СписокУслуг` проверяется в BSL-коде. Строки с `ПерерасчетНачислений = ОставитьБезИзменений` не считаются покрывающими кандидата.
